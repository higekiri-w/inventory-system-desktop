## Goal

Goal Invariant:

### 最小完了条件

- 開発用の Windows で作った MSI を入れると、入った folder（`C:\Program Files\在庫管理システム\`）の実行 file は main の 1 つだけで、`generate_bindings.exe`・`generate_traceability.exe`・`seed_demo_data.exe` が無い。入れたアプリは今までどおり起動する（L3）。
- 開発者・CI・script・docs の `cargo run --bin generate_bindings` / `generate_traceability` / `seed_demo_data` の呼び出しは、書き換えずに今までどおり動く。
- `cargo test`・clippy・fmt の gate は、移した 3 つの bin とその test を今までどおり含む。
- 外し方と理由が D-137 にあり、tauri の crate に開発用の bin を戻すと test が赤になる。

### 失敗定義

- MSI（または同じ binary の一覧を使う Linux の deb）に開発用の bin のどれかが入る。
- MSI が build できない、または入れたアプリが起動しない。
- `cargo run --bin <開発用の bin>` が CI・pre-push・local-ci・手順書のどこかで失敗する。`npm run tauri dev` が main を起動しない。
- generator の test が `cargo test` で回らなくなる、clippy・fmt が移した file を見なくなる（gate が黙って弱まる）。
- `generate_traceability` が repo の root を取り違え、`90-traceability.md` の再生成や `--check` の結果が変わる。

### 非目的

- 開発用の bin の中身・CLI の引数・出力の変更。
- 開発用の PC の `src-tauri/target/` の掃除、前の MSI（PR #191 の版）で開発用の Windows に既に入っている開発用の exe の扱い（店の PC は初回から本 lane の後の版で入る）。
- tauri-cli・tauri の版の更新。CI に Windows の build を足すこと。
- 履歴の文書（`docs/archive/**`・`docs/research/**`・decision-log の過去の D・`docs/DEV_SETUP_CHECKLIST.md` の完了の記録）の path の書き換え。

Priority: `Goal Invariant > Acceptance Criteria > supporting evidence`。AC や証跡作業が Goal Invariant を前進させない場合は、Goal を置き換えず簡略化・defer・削除する。

### Gated Amendment 1: dev-tools の bin に Windows の manifest を入れる（2026-10-29、L3-3 の FAIL の是正）

事実: L3 の 1 回目（head `c68ee7fa`）で `generate_bindings` だけが、自分の出力を出す前に `exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND`（dialog「プロシージャ エントリ ポイント TaskDialogIndirect が … generate_bindings.exe から見つかりませんでした」）で止まった。`seed_demo_data -- --help` と `generate_traceability -- --check` は `exit=0`。`TaskDialogIndirect` は Common Controls の v6 にだけあり、v6 を使うには実行 file の manifest に v6 の依存が要る。tauri の crate の bin は `src-tauri/build.rs` の `tauri_build::build()` からその manifest を受けるが、dev-tools の bin は受けない（下の出所）。3 つのうち `generate_bindings` だけが当たるのは、lib の `export_specta_bindings` を通して tauri の command の全部を link するからと読める（`seed_demo_data` は lib の `db`・`seed_demo` だけ、`generate_traceability` は lib を使わない。`use` の実読。Windows での切り分けはしていない）。

手段の梯子（AGENTS.md の「最小の実装（D-147）」）:

1. 要るか: 要る。AC12 が L3-3 の PASS を merge の条件にし、手順書の予行演習の準備と CI の外の開発者の Windows が `cargo run --bin generate_bindings` を使う。
2. repo にある手段: tauri の crate の `tauri_build::build()` を dev-tools でも呼ぶ形は、`tauri.conf.json` と icon と ACL の生成を dev-tools に持ち込み、tauri-build を dev-tools の build-dependency に足す（外部の crate の増えは無いが、bin の数だけの Windows の resource を作る大きな仕組みで、manifest の 1 つのために要らない）。採らない。
3. 標準の機能: Cargo の build script の `rustc-link-arg` と MSVC の linker の `/MANIFEST:EMBED`・`/MANIFESTDEPENDENCY` で、manifest の file も resource の compiler も要らない。これを採る。

事実: L3 の 2 回目（owner、Windows、head `fb3304c5`、2026-11-01）で L3-3 は PASS した（3 つの bin が debug の `cargo run` で `exit=0`、`git status --porcelain` が空。Gated Amendment 1 の manifest が効いた）。続く用意 1 の `npm run tauri build` が、dev-tools の release の bin（`generate_bindings`・`seed_demo_data`・`generate_traceability`）の link で `error: linking with link.exe failed: exit code: 1120` で止まった。owner の Windows の verbose の log（`C:\Users\<user>\l3-201\tauri-build-verbose.log`。要点だけを写す）: 先頭に `…\src-tauri\target\release\build\inventory-system-tauri-scaffold-<hash>\out\msvcrt.lib : warning LNK4003`（ライブラリの形式が無効、無視）、続けて `mainCRTStartup`・`memcpy`・`memset`・`memcmp`・`memmove`・`strlen`・`wcslen`・`atexit`・`__CxxFrameHandler3`・`_CxxThrowException`・`_tls_index`・`_fltused`・`__chkstk`・`type_info::vftable` の `LNK2001`/`LNK2019` と `fatal error LNK1120: 14 件の未解決の外部参照`（`generate_bindings.exe`）。C の runtime が丸ごと link されていない。
